# 实盘账户：只读同步

**一句话**：把券商导出的成交/持仓文件读进来，算盈亏和纪律位，**从不发单**。

## 为什么只能"读"

2026-08-28 中证协与中基协联合发布《证券公司交易信息系统接入管理规范》，随后券商开始排查：

- 能通过接口直连券商柜台、程序自动下单的通道，**仅限机构客户**；
- 严禁个人通过"类外接"方式开展程序化交易，**明确点名"包括文件交互服务"**；
- 券商清理"反采"（软件反过来抓券商数据），2026 年 11 月完成第一阶段整改。

证监会在《证券市场程序化交易管理规定》里另有一条：**先报告、后交易**。

所以边界很清楚：

| 动作 | 性质 | 现在能不能做 |
|---|---|---|
| 读对账单、算持仓、算盈亏 | 记账 | 可以，完全自动 |
| 程序生成委托发给券商柜台 | 程序化交易 | 个人只能通过券商自有终端（QMT / miniQMT / Ptrade），且需报备 |

**越过这条线的动作是第一行 `POST /order`，不是 `import`。** 本项目里没有那一行，这是设计。

## 三种拿到数据的方式

| 方式 | 门槛 | 说明 |
|---|---|---|
| 交割单 / 对账单导出 | 无 | 推荐。券商 PC 客户端都能导 CSV/Excel |
| QMT / miniQMT / Ptrade | 20 日日均 10 万起（头部 30–50 万）、C4/C5、6 个月实盘经验、报备 | 唯一"实时自动"的合规路径 |
| UI 自动化 / 逆向接口 / 第三方代管密码 | 无 | 违规，且正在被清理，不要做 |

## 日常怎么用

```
# 1) 把券商导出的文件丢进这个目录（csv / xlsx / txt 都行）
data/external/drop/

# 2) 收盘后自动跑，也可以手动
.venv/Scripts/python.exe scripts/external.py import
.venv/Scripts/python.exe scripts/external.py report --reconcile

# 3) 还没有导出文件时，先手工记一笔
.venv/Scripts/python.exe scripts/external.py add --symbol 000700 --side BUY \
    --qty 100 --price 13.07 --date 20261026 --fee 5.01
```

计划任务（`scripts/install_external_tasks.ps1` 注册）：

| 任务 | 时间 | 做什么 |
|---|---|---|
| `quant-desk-external-preopen` | 工作日 09:26 | 盘前竞价线检查，开盘前 4 分钟 |
| `quant-desk-external-close` | 工作日 17:35 | 导入新文件 + 收盘报告 + 对账 |

日志 `data/external_job.log`；触发纪律时另写 `data/external/ALERT.txt`（看板会红字显示）。

## 三个工程细节

**① 幂等靠内容哈希。** 同一个文件重复导入，第二次是 `duplicates=3, inserted=0`。同一天的两份不同导出（比如上午一份、下午一份）也只会各写一次，因为成交的键是 `日期+时间+代码+方向+数量+价格+券商成交编号`。

**② 流水不够，必须对账。** 分红送股、转股、配股都会改持仓但不产生成交。所以 `report --reconcile` 用**持仓快照**核对流水，有差异就说出来，并以快照为准。

**③ 两个锚点不能混。**
- **止损**锚在**买入价**（`13.07 × 0.95 = 12.42`），不含手续费——止损是市场交易的价格，不该因为你的佣金不同而不同。
- **竞价线**锚在**最近收盘**（`13.07 × 0.98 = 12.81`），因为明天的跳空是相对今晚的收盘。
- **当日盈亏**：当天开的仓用成本算（买在 13.07 就没有赚到 11.88→13.07 那段），隔夜的才用前收盘。

用错锚点会出现"同日同票两个止损"，这正是 2026-10-26 复盘里 12.42 和 12.46 打架的原因。

## 换一家券商

列名不写在代码里，写在 `configs/broker_map.json`。加一个券商 = 把它的列名加进对应字段的别名数组：

```json
"symbol": ["证券代码", "股票代码", "证券编码", "代码", "symbol", "ts_code"]
```

程序先在前 12 行里找表头（很多导出带标题行），再用 `required` 里的字段能否全部命中来选 profile。**解析失败时会把真实表头原样打印**——贴回来就能补别名，不用重写解析器。

## 它和模拟盘的关系

分离的两本账，永远不合并：

- **模拟盘**（`data/paper.sqlite`）是**测量**：20 笔平仓决定这套系统有没有 edge。混入真实成交会让那个数字既不回答问题 A 也不回答问题 B。
- **实盘**（`data/external.sqlite`）是**事实**：你真正持有的东西，只需要被准确描述。

看板上是两张卡片：`账户（模拟）` 和 `实盘（账外，只读）`。

## 数据到底怎么进来

券商不提供个人 API，所以"读真实账户"只有三条路，前两条今天就能走：

| 路径 | 自动化程度 | 前置条件 |
|---|---|---|
| 导出成交/持仓文件 | 半自动（导出一次，其余全自动） | 无 |
| QMT / miniQMT / Ptrade | 全自动、实时 | 20 日日均 10 万起、C4/C5、6 个月实盘经验、报备 |
| UI 自动化 / 逆向接口 | —— | **违规**，2026-11 整改期，不要碰 |

### 第一种：导出文件（现在就能用）

券商 PC 客户端一般是「查询 → 成交明细 / 对账单 → 导出」，网上营业厅也有「交割单查询」。
导出的文件丢进：

```
data/external/drop/
```

17:35 的任务会自动 `import`，也可以手动：

```bash
python scripts/external.py import --dry-run    # 先看能不能解析
python scripts/external.py import              # 真导入（幂等）
python scripts/external.py report --reconcile  # 盈亏 + 纪律位 + 对账
```

**三种伪装成 `.xls` 的格式都已经处理**，这是实测过的，不是猜的：

| 形态 | 例子 | 处理 |
|---|---|---|
| 真 Excel | openpyxl / xlrd 能开 | 直接读 |
| **HTML 表格改名 `.xls`** | 网页版交割单"导出 Excel" | `read_excel` 会报 `Excel file format cannot be determined`，改用 `read_html` 挑命中列名最多的那张表 |
| 文本带标题行 | 首行是"成交明细"，第二行才是表头 | 先按分隔符出现次数选 sep，再找表头行 |

编码也覆盖了：`utf-8-sig` / `gbk` / `utf-8` 依次尝试——中文 Windows 客户端导出的多是 GBK。

### "同步变化"具体同的是什么

三种变化，两条通道，缺一不可：

| 变化 | 从哪来 | 为什么不能只靠流水 |
|---|---|---|
| 买卖 | 成交流水（增量） | —— |
| 分红送股、转股、配股 | **持仓快照**（差异） | 不产生成交记录，只改股数 |
| 资金变动（银证转账） | 对账单里的资金流水 | 不算交易，但会改变可用资金 |

所以每次导入都会跑 `reconcile`：流水算出的持仓 vs 券商快照，不一致就报警，**以快照为准**。
没有导入过快照时，它会明说"只核了流水"，而不是假装一致。

### 第二种：QMT（要真实时）

QMT/miniQMT 能读到实时持仓与成交，落进同一个 `data/external.sqlite` 即可：
`ExternalStore.add_trades()` 和 `save_snapshot()` 是与格式无关的入口，写一个 20 行的 adapter 就够。
但门槛是 10 万日均资产、C4 风险测评、6 个月实盘经验，以及券商的程序化报备。

**它仍然不发单。** 能下单和该不该由这个系统下单是两件事，后者我们讨论过：没有 edge 之前，自动化只会更快地亏。

## 用本机的同花顺取数

本机已装同花顺（`D:\同花顺`）。它是行情终端 + 内嵌的券商委托模块，**账户数据只存在于运行时**：
目录里只有 `xiadan.ini` / `system.dat` / `config` 这类配置，没有任何持仓表或成交表。
所以"进去把数据拿出来"只有两条实际可走的路，都不需要程序去操作客户端窗口。

### 路线一：复制粘贴（推荐，最快）

```
同花顺 → 交易/持仓 页面 → 点表格里任意单元格 → Ctrl+A → Ctrl+C
回到命令行：
    python scripts/external.py paste --dry-run    # 先看认出什么，不写库
    python scripts/external.py paste              # 真导入
```

`paste` 读的是 Windows 剪贴板，不在同花顺里点任何东西、不抓窗口、不读它的内存。
它能自动分辨你复制的是**持仓**还是**成交**（按表头里有哪些已知列名），
所以两个页面用的是同一条命令。

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只解析，打印前几只和行数 |
| `--as-of 20261024` | 补历史：把这份持仓记成某一天的快照 |
| `--profile positions` | 强制按持仓解析（自动识别失败时用） |
| `--text "…"` | 直接给文本，不碰剪贴板（调试用） |

复制出来的常见形态都已经测过：制表符分隔、带 `合计` 汇总行（会被跳过）、
`可用余额=0`（T+1 当日买入不可卖，会如实记成 0）。

### 路线二：导出文件

持仓页右键 → 导出 / 导出数据（有的版本在"数据"菜单里），存到：

```
data/external/drop/
```

17:35 的任务自动导入；也可以 `python scripts/external.py import`。
导出比复制多一样东西：**成交明细有流水号**，能做逐笔去重和费用核算；
复制持仓只有快照，适合"每天对一次总账"。

**建议的节奏**：每天收盘 `paste` 一次持仓（10 秒），周末导一次成交明细（补流水）。

### 为什么不做"读屏"

技术上能写，但三条都不划算：

1. 同花顺的表格是**自绘控件**，UI Automation 取不到单元格文本，只能截图 OCR；
2. 分辨率、缩放、窗口遮挡、行高任一变化，就可能把 `13.07` 读成别的数——
   而账本最怕的正是一个错数字被当成真的，它不会报错，只会让后面每个结论都偏；
3. 这条路要求客户端在前台、不能最小化，等于把"每天跟"绑死在"电脑得开着这个窗口"上。

对比一下：复制粘贴是**你按两个键**，准确率 100%，不需要任何自动化。

### 为什么不去"登录你的账户"

我不会碰你的账号密码。原因不是技术，是三条硬边界：

- 2026-08 中证协/中基协《证券公司交易信息系统接入管理规范》明确禁止个人"类外接"，
  并把**第三方代管凭据**列为重点清理对象；
- 登录动作本身产生的是委托会话，一旦由程序发起，性质就从"记账"变成"接入"；
- 你的密码一旦经过我这层，它的安全性就只等于这台机器上最弱的那一环。

**登录必须你本人做。** 登录之后，数据用上面两条路出来——都是只读，都不产生委托。

### 一个必须记住的前提

`paste` 写的是**持仓快照**，它不解释股数为什么变。分红送股、转股、配股都不产生成交记录，
只改股数，所以快照会和"成交流水累加出来的持仓"对不上——这时 `paste` 会打印：

```
[warn] 对账有 1 处差异（分红/转股/漏导？以快照为准）：
   002966.SZ 流水 0 vs 快照 200（差 +200）
```

差异**不是错误**，是它在告诉你：这 200 股没有对应的买入流水，要么是漏导了成交，
要么是非交易过户。以快照为准，然后去补那份成交明细。

## "能不能实时读"：先测，不要猜

有人说同花顺的表格是自绘控件、UI Automation 读不到。这句话可能是对的，但**这台机器上没人验过**。
而且它有一个很容易混淆的反例：Chromium 类界面默认**关闭**可访问性树，不唤醒时读出来也只有容器，
看起来和"自绘"一模一样。

所以先跑一个只读探针，用结果决定后面写什么代码：

```bash
# 同花顺登录后，切到持仓页面，然后：
.venv/Scripts/python.exe scripts/probe_ui.py --match 同花顺 --tree
.venv/Scripts/python.exe scripts/probe_ui.py --list        # 不知道标题叫什么就先列出来
```

探针只读：不点击、不输入、不切换窗口，只读 Windows 已经公开的可访问性数据，
并给 Chromium 的渲染控件发一次 `WM_GETOBJECT`（这是"请把树建起来"的正式请求）。

### 实测：唤醒是有效的

在 WorkBuddy（Electron/Chromium）窗口上，同一棵树：

| | 节点 | 有名字的元素 |
|---|---|---|
| 直接读 | 7 | 1 |
| 发送 WM_GETOBJECT 后 | **287** | **241** |

也就是说，"读不到"至少有三种完全不同的原因，处置方式相反：

| 现象 | 原因 | 处置 |
|---|---|---|
| 节点很少、命名元素 ≤ 2 | 没登录 / 没切到持仓页 / 真的是自绘 | 先切页面；仍是这样就只能截图 |
| 节点多、有文字、但没有 6 位代码与价格 | 树开了，数值不在文本层 | 自绘表，OCR 是唯一路 |
| 有代码、有价格、还有 `DataItem`/`Header` | **可读** | 写读取器，准确率和导出一样 |

### 如果探针说"可读"

那就能做到你要的实时，而且不需要截图识别：

- 按窗口里的行/列结构还原成表格（不是按像素猜，是按元素结构读）；
- 每 N 秒读一次，写进 `data/external.sqlite`，`source` 标成 `screen:ths`，和导入的流水分开；
- **写之前先自检**：`股数 × 成本 ≈ 市值`、代码必须是 6 位、同一只票的行不能重复。
  自检不过就不写，报一行"这次读到的数不自洽"，而不是把一个错数字记进账本；
- 快照与流水照旧对账，冲突时以快照为准。

### 如果探针说"不可读"

那就只剩截图 OCR。它的代价不是"写起来麻烦"，而是**错一个数字不会有任何提示**：
`13.07` 读成 `13.07` 之外的数，账本照收，后面所有结论都偏。所以那时我会把它做成
"读出来先给你看一眼、你确认才入库"，而不是无声自动同步。

**判据永远是同一条：宁可缺一天，不写错一个数。**

## 实测：哪些能读，哪些读不到（2026-10-27）

登录后在同花顺的独立下单程序（`xiadan.exe`，窗口 `网上股票交易系统5.0`）上实测：

| 对象 | 控件 | 可读性 |
|---|---|---|
| 资金面板（总资产/可用/市值/持仓盈亏） | 标准 `Static` | **可读**，`GetWindowTextW`，不抢焦点、不按键 |
| 侧边导航 | `SysTreeView32` | 可读（页签名） |
| **持仓明细表** | `CVirtualGridCtrl` | **读不到**：UIA 只给一个容器，MSAA `accChildCount = 0` |

### 所以用了什么、放弃了什么

**账户级：`service/trading/ths_account.py`** — 每几秒读一次资金面板，返回值经过一条恒等式校验：

```
总资产 ≈ 可用金额 + 股票市值
```

同一棵窗口树里叠着 A股与港股两套面板，同一个标签有两个值。不猜哪一个，而是找出让上式成立的组合；
没有组合成立就返回 `ok: false` 和原因。实测（12:30）：总资产 4,813.37 / 可用 3,173.37 / 市值 1,638.00，
残差 2.00 元（利息或 在途），连读三次一致。

**明细表：放弃自动读。** `scripts/read_ths.py` 能靠 Ctrl+A / Ctrl+C 拿出来，但要抢焦点——
实测丢过一次：按键落到了别的程序上，复制回 233 行无关文本。现在它默认**不发送任何按键**，
必须显式加 `--press-keys`，且只作为"手动对一次账"的工具，不进任何定时任务。

### 正确的拼法：日频明细 + 实时行情 + 账户级校验

股数只在交易时变，价格每分钟都在变。所以：

| 需要什么 | 从哪来 | 频率 |
|---|---|---|
| 持仓明细（代码/股数/成本） | 导出或 `paste` | 每天一次，或每次成交后 |
| 每只票的现价 | 项目自己的行情源（`ths`） | 实时 |
| 账户总额、可用、市值 | 你在面板里手填（每天一次，之后每笔成交自动扣加） | 按需 |
| 一致性 | 我方按行情算的市值 vs 面板市值 | 差异 > 1% 即"持仓变了，请更新明细" |

这样盘中一次都不碰客户端，却能做到：市值实时、盈亏实时、回撤与单日亏损告警实时，
并且当明细过期时会明确告诉你，而不是拿旧股数算出一个看起来正常的数。

### 想要"每只票都实时"，只有一条路

QMT / miniQMT（迅投）是本机进程 + Python API，能读实时持仓与成交。门槛：20 日日均资产
10 万起（部分券商 30–50 万）、C4/C5 风险测评、6 个月实盘经验、程序化报备。当前账户 4,813 元，
差一个数量级——**在这个规模上谈 QMT 不现实**，等资金到位再上，接口已经按格式无关留好
（`ExternalStore.add_trades()` / `save_snapshot()`）。

> **2026-10-27 起停用。** 面板不再主动读客户端：账户总额、可用资金与持仓都由用户
> 在面板里自己录，成交由「记一笔」录入并自动算费。下面这套读屏保留为**排障工具**
> （`scripts/sync_today.py`），不进任何定时任务，面板里也没有入口。原因很简单——
> 它依赖客户端停在某一页、依赖缩放与字体，换台机器就失效，而一次读错会把止损锚
> 到错的价格上。手填慢十秒，但它不会悄悄错。

### 零操作读取：`PrintWindow` + 系统 OCR（2026-10-27 实测可用，现已降级为排障工具）

发现一条不需要你动手、也不需要窗口在前台的路：

1. **`PrintWindow(grid, hwnd, PW_RENDERFULLCONTENT)`** —— 请窗口把自己画到内存位图上。
   实测：一个被 WorkBuddy 完全遮住、不在前台的持仓表，照样画出了完整的 905×360 表格。
   这一步是整条路成立的前提，因为截屏（ImageGrab）只能拿到屏幕上看得见的部分。
2. **Windows 自带 OCR**（`Windows.Media.Ocr`，中文引擎 `zh-Hans-CN`，无需下载模型）。
   它认得每个数字，但会**丢掉小数点**（`9.035` → `9` + `035`）、**丢掉负号**、
   并把名字两个字的顺序读反（古汉医药 → 古汉药医）。
3. **重建 + 自校验**（`scripts/read_ths_screen.py`）：
   - 用表头片段的 x 坐标定出列；
   - 小数位**不猜**：枚举 0–3 位的全局排法，选让「Σ 数量 × 市价」最接近账户面板
     `股票市值`、且每行 `数量 × (市价 − 成本价) ≈ 盈亏` 都成立的那一种；
   - 名称用代码从 `stock_basic` 校正，不用 OCR 的字；
   - 与面板对不上就**拒绝写库**。

实测输出：

```
[scale] 成本3位/市价3位/盈亏3位 小数；1/1 行自证通过；合计 1,638.00
   000590.SZ 古汉医药  200 股 成本 9.035 市值 1,638.00 盈亏 -169.00
[check] 面板市值 1,638.00 vs 读出 1,638.00（差 0.00）
```

**这套方法的弱点必须说清楚**：同一串数字 `9035/8190/169000` 在 0–3 位小数下都能自洽
（盈亏方程两边同比缩放）。所以小数位**完全由账户面板决定**——面板若读错，它会跟着错。
面板是另一条独立通道（`Static` 文本）读来的，两者同时错才会漏。测试里专门钉了这一点。
